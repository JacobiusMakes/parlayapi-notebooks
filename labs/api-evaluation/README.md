# A small API evaluation you can explain

Start with one output, one required scope and one acceptance rule. A successful
request is useful evidence about transport. Your project still needs the
particular result that answers its question.

[Open the evaluation workbench](https://parlay-api.com/tools/evaluation-lab?utm_source=github&utm_medium=recipe&utm_campaign=api-evaluation)
to build a requirements brief, compare entered fields and draw a polling window.
No account or API key is needed. The workbench checks the fields you enter; it
does not make an API request or authenticate a response.

## Work one polling window

Suppose a fictional job runs for seven minutes and refreshes every five minutes.
Its active window includes the initial poll and excludes a poll at the end.

| Proposed time | In this window? | Reason |
|---|---|---|
| 0 seconds | Yes | Initial poll at the start |
| 300 seconds | Yes | Still inside the 420-second window |
| 600 seconds | No | After the window ends |

That means two polls per active day, not one. With two separately polled sports,
three requests per sport per refresh, and two active days:

```text
2 polls x 2 sports x 3 requests x 2 days = 24 base requests
5 percent additional retries: round up 1.2 to 2 requests
24 + 2 = 26 proposed requests
```

[Download the worked polling assumptions](polling-window.example.json).
The file is a labelled teaching example generated by the workbench's calculation
core. Credit cost is unknown. For a credit estimate, use the
[workload planner](https://parlay-api.com/tools/api-workload?utm_source=github&utm_medium=recipe&utm_campaign=api-evaluation)
and enter a unit cost verified for your exact request shape.

Try changing the active window to exactly five minutes. Under the same boundary
rule, only the poll at zero is inside it. Changing the number of displayed
widgets alone does not establish a need for additional API requests; list the
actual request shapes and pages your project needs.

## Make the required result explicit

The [example requirements brief](requirements-brief.example.json) asks for an
invented event, bookmaker and market. Its acceptance rule requires the reviewer
to inspect the exact record, price and observation time. It does not claim that
ParlayAPI currently supplies that requested scope.

The [example field check](record-field-check.example.json) shows a deliberately
unmet age rule. The entered observation is 60.000001 seconds before the explicit
as-of time, one microsecond beyond the declared 60-second limit. The identity
fields and presence checks pass while the selected age limit fails. There are
no real source observations in these example files.

Change one requirement or one entered field at a time in the workbench. A wrong
event must remain a mismatch. A missing observation time must remain unknown,
even if no age limit was requested. Matching the entered fields proves only
those local checks.

## Take the brief into a private integration

Read the [useful-result guide](https://parlay-api.com/tools/useful-result-guide?utm_source=github&utm_medium=recipe&utm_campaign=api-evaluation)
and the current [first-call documentation](https://parlay-api.com/getting-started).
Use your own account and key privately. Verify exact entitlement, identifiers,
market, request cost and the documented meaning of each timestamp.

Keep keys and private API responses out of GitHub issues, commits and shared
notebooks. These public examples are intentionally invented. A real task needs
its own source evidence and the intended recipient's acceptance. A download,
signup or HTTP success is a separate observation.

If you are ready for your own integration,
[create an account](https://parlay-api.com/signup?utm_source=github&utm_medium=recipe&utm_campaign=api-evaluation).
